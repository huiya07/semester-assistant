# 功能：学期视图与课表数据（2026-10-25）

## 目标
把「课表 + 作业 + 周一日期」接成一条时间轴，回答「这周该做什么」。

## 关键提问（原文摘录）
1. 「作业数据不好造，因为开学前两周好多课程都没作业。」
2. 「课表的名字叫程序设计基础，你想一下啊。」
3. 「那就放弃『第三章是哪周学的』这条路。」

## 三次真实的纠偏

### 一、数据结构选错了：想按「每周固定作业」建模
最初打算给每门课每周排作业。灰鸦指出「开学前两周好多课程都没作业」——这说明作业是**稀疏事件**，不是周期性条目。
改为 `{id, course, title, due_date}` 的一维事件表，到日子才出现在视图里。
**结论：」真实数据的分布特征要先用用户的实际情况校验，不能按整齐的模型假设。**」

### 二、我把课名想当然：把「程序设计基础」当成编程课
课表里有「程序设计基础」「Python 程序设计」「数据库技术」，我按名字判断网页课不在课表里，
于是设计成「作业可以挂在不存在的课程上」。
灰鸦指出网页制作课在课表里的名字就是「程序设计基础」（周二/周五第 1-2 节，一周两次课推一个项目）。
**结论：课名不能按字面理解，要以实际排课和项目节奏反推。**

### 三、砍掉一个看起来很酷但数据不支持的功能
曾计划支持「第三章是哪周学的」。查课表结构后发现：课表只有「课程 / 周几 / 第几节 / 哪几周上」，
**没有任何教学进度信息**。
两条出路：上传资料时人工标注第几周（演示时要人肉填，反而显得不智能），或者放弃。
灰鸦决定放弃。
**结论：功能取舍要问「数据支不支持」，不问「看起来酷不酷」。**

## 实现要点
- **周次**：第 1 周从 `SEMESTER_START`（2026-09-07）起算，`(d - start).days // 7 + 1`
- **作业稀疏**：`assignments_due_on(d)` 只返回当天到期的；`upcoming_assignments(d, 14)` 给未来两周
- **脱敏**：转换工具只保留 `name/day/start_section/end_section/weeks/start_time/end_time`，
  教师姓名与教室直接丢弃。已验证生成文件里 `teacher` / `position` 出现 0 次
- **边界**：早于开学日返回 `before_semester=True`，界面提示「学期还没开始」，不再算出「第 -5 周」

## 结论
学期视图的难度不在算法，在数据：课表是现成的（拾光导出 JSON，43 条），
作业必须自建，且真实的作业分布是稀疏不均匀的。
「时间轴 × 知识库」这个差异点成立，但**章节级的进度映射没有数据支撑，不做**。

## 实测结果
`week 2026-10-30`：第 8 周 / 17 节 / 周五同时显示「程序设计基础」课程与「项目三 姑苏美食」作业截止。
